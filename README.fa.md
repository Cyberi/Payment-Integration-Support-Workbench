# آزمایشگاه پشتیبانی و عیب‌یابی یکپارچه‌سازی پرداخت پذیرندگان

> **فقط شبیه‌سازی.** این پروژه پرداخت واقعی انجام نمی‌دهد، به هیچ درگاه یا بانکی وصل نیست و هیچ داده واقعی مشتری ندارد. همه پذیرنده‌ها، سفارش‌ها، پرداخت‌ها و webhookها ساختگی هستند.

## هدف پروژه
این یک نمونه‌کار برای نقش‌های **پشتیبانی فنی، Application Support و Payment Integration Support** در شرکت‌های غیربانکی (فین‌تک، پرداخت‌یار، نرم‌افزارهای مالی و SaaS با جریان مالی) است. نشان می‌دهد یک رخداد را از گزارش پذیرنده تا شواهد فنی، علت احتمالی، راهکار، تست بعد از رفع و پیام به پذیرنده چطور دنبال می‌کنیم.

## چه چیزی واقعاً کار می‌کند
- ایجاد سفارش و پرداخت، استعلام وضعیت (verify) از ارائه‌دهنده ساختگی.
- ارائه‌دهنده شبیه‌ساز که موفقیت، شکست یا انقضا را تعیین می‌کند و webhook امضاشده می‌فرستد؛ می‌تواند webhook را نفرستد، دوبار بفرستد، امضای نامعتبر بزند یا timeout بدهد.
- بررسی امضای HMAC، جلوگیری از پردازش تکراری با `event_id`، بررسی مبلغ و ثبت همه تحویل‌ها.
- Idempotency-Key: درخواست تکراری با همان بدنه پاسخ قبلی را برمی‌گرداند؛ کلید تکراری با بدنه متفاوت HTTP 409 می‌گیرد.
- استرداد آزمایشی جزئی و کامل با سقف مبلغ قابل استرداد.
- تبدیل واحد ریال/تومان فقط در یک نقطه و بدون اعشار (مبلغ داخلی همیشه ریال و عدد صحیح است).
- خط زمانی یک پرداخت یا یک correlation ID شامل لاگ‌ها، رویدادها، استردادها و یادداشت‌های پرونده.
- پرونده پشتیبانی با ساختار ۱۱ مرحله‌ای؛ تا شواهد و تست بعد از رفع ثبت نشود، وضعیت «حل‌شده» و «بسته‌شده» نمی‌گیرد.
- تطبیق گزارش CSV ساختگی با پنج نوع مغایرت؛ هیچ ردیفی حذف یا مبلغی اصلاح نمی‌شود.
- ده راهنمای عیب‌یابی فارسی با نشانه، شرط اجرا، بررسی‌ها، اقدام مجاز و ممنوع، شرط ارجاع و پیام نمونه به پذیرنده.
- کنسول فارسی راست‌به‌چپ، بدون JavaScript و بدون CDN.
- مجموعه Postman و نمونه‌های curl.

## اجرا

**پیش‌نیاز:** Python 3.12 یا بالاتر. نصب بسته‌ای لازم نیست.

**ویندوز (PowerShell):**
```powershell
py -3.12 -m scripts.reset_demo_data
py -3.12 -m app.main
```

**لینوکس / macOS:**
```bash
python3.12 -m scripts.reset_demo_data
python3.12 -m app.main
```

سپس مرورگر را روی http://127.0.0.1:8000 باز کنید.

`scripts.reset_demo_data` دیتابیس را از صفر می‌سازد، سناریوها را اجرا می‌کند و هشت پرونده پشتیبانی نمونه باز می‌کند. خروجی موفق:
```
reset done. merchants=2 scenarios_ok=9/9 cases=8 reconciliation_exceptions=5
```

## تست‌ها
```bash
python -m unittest discover -s tests -t . -v
```
نتیجه آخرین اجرا در همین مخزن: `Ran 18 tests` و `OK`. تست‌ها ۱۲ مورد خواسته‌شده در پرامپت را پوشش می‌دهند؛ از جمله timeout که تا verify به وضعیت `unknown` می‌ماند، webhook تکراری بدون اثر دوباره، امضای نامعتبر، idempotency، سقف استرداد، تبدیل واحد، تشخیص مغایرت، جست‌وجوی timeline با correlation ID، قوانین بستن پرونده و نبودن secret در لاگ.

## یک سناریوی نمونه: از گزارش تا حل
پرونده **CASE-1001** را در کنسول باز کنید. پذیرنده می‌گوید مشتری پیامک موفقیت دارد ولی سفارش هنوز «در انتظار پرداخت» است. با `GET /api/v1/payments/{id}` و خط زمانی می‌بینیم webhook موفق دریافت نشده. با `verify` از ارائه‌دهنده وضعیت را می‌گیریم؛ پرداخت موفق و سفارش پرداخت‌شده می‌شود. verify دوم چیزی را تغییر نمی‌دهد. پیام به پذیرنده نوشته و پرونده با شواهد بسته می‌شود.

## محدودیت‌ها
- امنیت این پروژه آموزشی است: کلید API و secret نمونه در `.env.example` هستند، ورود کاربر و نقش‌ها وجود ندارد، TLS ندارد و فقط روی `127.0.0.1` اجرا می‌شود.
- هیچ ادعای PCI DSS، امنیت بانکی یا آمادگی تولید مطرح نمی‌شود.
- رفتار شبیه‌ساز یک مدل است؛ درگاه‌های واقعی ایران همه یک‌جور رفتار نمی‌کنند.
- تلاش مجدد webhook دستی است و سقف دارد؛ یک صف تلاش مجدد پایدار در نسخه بعد لازم است.
- متن فارسی هنوز توسط یک سرپرست پشتیبانی فارسی‌زبان بازبینی نشده است.
